# Project Documentation Principles

## Repository boundaries

Проект состоит минимум из трёх независимых GitHub-репозиториев:

* `plant-app-frontend`
* `plant-app-backend`
* `plant-app-docs`

`plant-app-docs` хранит глобальные знания о продукте и системе.

Документация, специфичная для конкретного приложения, хранится рядом с его кодом в соответствующем repository.

Принцип:

> Global knowledge lives in docs.
> Code-specific knowledge lives with code.

Frontend и backend не должны зависеть от того, что `plant-app-docs` находится рядом с ними в локальной файловой системе.

Для доступа AI-агентов к общей документации используется GitHub connector/plugin.

В каждом кодовом repository будет короткий `AGENTS.md`, который указывает агенту на `plant-app-docs` как на source of truth для глобальной проектной документации.

## Documentation formats

Используем:

* Markdown — знания и описания
* Mermaid — технические схемы
* ADR — архитектурные решения и причины их принятия
* Figma — визуальный дизайн
* GitHub Issues — задачи и backlog
* Code — реализация

## Documentation philosophy

Не документируем всё подряд.

Предпочтительнее небольшое количество актуальной документации, чем большая база документов, которую приходится постоянно синхронизировать с кодом.

Документация создаётся тогда, когда она действительно помогает разработке, архитектуре или AI-агентам понимать проект.

## ADR

ADR должны быть краткими и содержательными.

ADR создаётся для значимых решений, у которых:

* были реальные альтернативы;
* важно сохранить причину выбора;
* решение потенциально может быть пересмотрено в будущем.

ADR не используется для фиксации мелких implementation details.

## Разделение проектной информации

Используем следующее разделение:

* `plant-app-docs` — что представляет собой система и почему она устроена именно так;
* GitHub Issues — что необходимо сделать;
* Pull Requests — как конкретная задача была реализована;
* Code — фактическая реализация системы.

GitHub Issues не используются как долговременная проектная документация.

## Язык проектной коммуникации

Проектная документация, GitHub Issues, Pull Request descriptions и основная коммуникация по проекту ведутся на русском языке.

Код, названия сущностей, API, файлов, функций, типов и другие технические идентификаторы используются на английском языке.

## Development workflow

Основной workflow разработки:

GitHub Issue → реализация AI-агентом → Pull Request → code review → исправления → merge.

AI-агент может создавать Pull Request после реализации задачи.

Разработчик проводит code review через GitHub UI и может оставлять комментарии непосредственно к изменённому коду.

AI-агент должен учитывать review-комментарии и вносить необходимые изменения в тот же Pull Request.

Финальное решение о принятии изменений и merge остаётся за разработчиком.

## AI context

`AGENTS.md` не должен превращаться в полную документацию проекта.

Его задача — дать агенту:

* основные правила работы с конкретным repository;
* ссылки/указатели на необходимые источники знаний;
* понимание, где находится глобальная документация;
* инструкции о том, какую документацию необходимо проверить перед изменениями.
